## Симптом

В комментарии «Статус УЛ»:

```
Ключ УЛ: ('8950', 'pos3', 'bcc0000659')
Распределено поштучных поставок: 0
Fallback сопоставления: CODE_MTO='bcc0000659'
```

«0» = сколько единиц **этой строки** забрали из очереди УЛ, не «в УЛ ноль». Очередь по `CODE_MTO` нашлась; списания не было. Остатки очереди уходят в **«Только в УЛ»**.

Прогон (ориентир): `_результат_проверки_2026.08.18.14.51` — `allocated=0`, `нет_в_УЛ≈9412`, `только_УЛ≈25895`. Смотреть `ul_compare_report_*.txt` и Excel-комментарии, не логи чата.

Основной профиль: `step4.include_packing_lists=true`, **`include_mto_vo_without_rfp_anchor=true`**.

## Почему так (два разных ключа)

1. Очередь УЛ: `_candidate_key` ищет `CODE → CODE_MTO → CODE_VO` среди ключей очередей `(title, system, code)`. Зачёркнутый MTO-код пропускается. Это **работает** — иначе не было бы строки Fallback.
2. Сколько списывать: `ordered = min(capacity, snapshot_remaining)`.
   - Снимок `build_ordered_snapshot(rfp_data)` **до** split/match, ключ = `parse_composite_title(DS_TITLE)` + **RFP `CODE`**.
   - `capacity` = `_row_capacity` ← колонка **`VALUES`** (RFP), не `VALUES_MTO`.
   - `primary_order_key` всегда из RFP `CODE`; если CODE пустой — подставляется UL-ключ, но снимка по MTO-коду всё равно нет.

Контракт смоука `test_code_fallbacks_and_struck_mto_exclusion`: fallback **должен** списывать, когда снимок есть по RFP-коду (`RFP-MISS` → очередь `MTO-OK`). Сейчас ломается не этот тест, а строки, у которых снимка/остатка по RFP `CODE` нет.

При `ordered=0` и `allocated=0` статус считается **«Поставка комплектна»** (`remaining=0`). Это маскирует дыру.

## Гипотезы (проверить по отчёту, не гадать)

**H1 (главная).** Строки «Добавлен из МТО» / из VO: `CODE` пустой, qty в `VALUES_MTO` / `VALUES_VO`, в снимке их нет. Fallback находит УЛ, `capacity=0` → `ordered=0` → очередь не трогается → «Только в УЛ». В основном JSON якорь MTO без RFP **включён**.

**H2.** RFP-код есть, но ключ снимка другой (другой `DS_TITLE` / остаток снимка уже съели split-соседи). Fallback срабатывает, списывать нечего — для соседей это может быть норма, для пустого CODE — нет.

**H3.** RFP `CODE` не попал в снимок (пустой/битый qty на исходной position_row), после матча заполнился `CODE_MTO`.

Не чинить «просто искать снимок по UL-ключу»: для H1 в снимке MTO-ключа нет; для нормального fallback (RFP-MISS) снимок как раз по RFP-коду.

## Предложения по починке

### 0. [C2] Диагностика до патча

По `ul_compare_report_*.txt` + выборке Excel:

- доля fallback с `allocated=0` vs `>0`;
- среди нулей: пустой `CODE` / `MATCH_STATUS=Добавлен из МТО` / ненулевой `VALUES_MTO`;
- не путать с `нет_в_УЛ` (ключ очереди не найден).

Критерий: одна таблица классов. Без неё не выбирать вариант B vs C вслепую.

### A. [C2] UX, даже если логику qty ещё не трогаем

Если очередь найдена, а `ordered=0` и `allocated=0` — не писать «Поставка комплектна». Явный статус/комментарий: «очередь УЛ есть, заказ для списания 0 (снимок/VALUES)». Иначе зелёный 0/0 вводит в заблуждение.

### B. [C2+V] Рекомендуемый фикс (H1)

Для строки, у которой очередь найдена fallback-кодом **и** RFP `CODE` пустой (или нет остатка снимка по `primary_order_key`):

- `capacity` брать из `VALUES`, иначе `VALUES_MTO`, иначе `VALUES_VO`;
- `ordered = min(capacity, длина очереди)` не годится как «заказ» без лимита: заказ = capacity, поставка = сколько реально pop;
- списание из **той же** очереди `queues[key]`;
- не дебетовать снимок RFP-кода, которого нет (нельзя украсть qty у другой RFP-позиции с тем же title).

Так «Добавлен из МТО» сравнивается с УЛ по коду МТО и количеству МТО. Остаток очереди по-прежнему «Только в УЛ».

Ограничение: два MTO-only ряда с одним ключом делят одну очередь по порядку allocation (сначала с тегами). Это совпадает с текущим FIFO.

### C. [PREMIUM] Не делать первым

Индексировать снимок ещё и по `CODE_MTO` **нельзя** на этапе `build_ordered_snapshot`: матча ещё нет. После матча строить второй индекс «алиасов» опасно: RFP-код и MTO-код — разные заказы, легко списать чужой снимок.

Исключение на потом: replacement table (старый RFP-код ↔ новый MTO), если диагностика покажет массовые пары не H1.

### D. Смоук, который должен упасть до фикса и пройти после

В `tmp/test_rfp_packing_compare_smoke.py`:

1. Строка как «Добавлен из МТО»: `CODE=""`, `CODE_MTO="MTO-OK"`, `VALUES=""`, `VALUES_MTO=2`, очередь УЛ на `MTO-OK` qty 2 → `allocated=2`, не «Только в УЛ» на эти 2, статус не complete-0.
2. Регрессия: оставить `test_code_fallbacks_and_struck_mto_exclusion` (снимок по RFP-коду, очередь по MTO).
3. Split-соседи с одним RFP-кодом и исчерпанным снимком не должны повторно грабить очередь через `CODE_MTO`.

Verification: `python tmp/test_rfp_packing_compare_smoke.py`.
